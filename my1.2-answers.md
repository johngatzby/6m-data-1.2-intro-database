# 🍔 FoodFast Database Design – My Answers

## Schema (DBML)

```dbml
Enum address_type {
  home
  work
}

Enum vehicle_type {
  bike
  car
}

Enum order_status {
  placed
  preparing
  out_for_delivery
  delivered
  cancelled
}

Table users {
  id int [pk, increment]
  name varchar [not null]
  email varchar [not null, unique, check: `email LIKE '%_@_%._%'`]
}

Table addresses {
  id int [pk, increment]
  street varchar [not null]
  city varchar [not null]
  type address_type [not null]
  user_id int [ref: > users.id, not null]
}

Table restaurants {
  id int [pk, increment]
  name varchar [not null]
  cuisine_type varchar
  rating decimal(2,1) [not null]
}

Table menu_items {
  id int [pk, increment]
  name varchar [not null]
  price decimal(10,2) [not null]
  restaurant_id int [ref: > restaurants.id, not null]
}

Table couriers {
  id int [pk, increment]
  name varchar [not null]
  vehicle vehicle_type [not null]
}

Table orders {
  id int [pk, increment]
  restaurant_id int [ref: > restaurants.id, not null]
  user_id int [ref: > users.id, not null]
  courier_id int [ref: > couriers.id]          // null until a courier accepts
  status order_status [not null, default: 'placed']
  created_at timestamp [not null, default: `now()`]
  delivery_address varchar [not null]          // snapshot at time of order
}

Table order_details {
  id int [pk, increment]
  menu_item_id int [ref: > menu_items.id, not null]
  order_id int [ref: > orders.id, not null]
  quantity int [not null, default: 1]
  purchased_price decimal(10,2) [not null]     // snapshot of price at purchase
  menu_item_name varchar [not null]            // snapshot of dish name at purchase
}
```

## Key design decisions

**Challenge 1 – Many-to-many:** One order contains many menu items, and one menu item appears in many orders (M:N). Neither table can hold a single foreign key for this, so `order_details` acts as a junction table: each row means "this order contains this dish". One M:N becomes two 1:N relationships.

**Challenge 2 – Price history:** `purchased_price` freezes the price at checkout, so a later menu price change doesn't rewrite old receipts or revenue reports. I applied the same "snapshot" idea twice more:
- `menu_item_name` – receipts keep the dish name the customer saw, even if renamed later
- `delivery_address` – orders keep where they were actually delivered, even if the user edits or deletes a saved address

The principle: **live tables hold what is true now; transaction tables freeze what was true then.**

**Nullable vs NOT NULL reflects the real lifecycle:** `courier_id` is nullable because an order is created *before* a courier accepts it. Forcing NOT NULL would mean faking a placeholder courier or delaying saving the order.

**Rules pushed into the database:** enums for `vehicle`, `type` and `status` block invalid values; `email` is NOT NULL, UNIQUE and must look like an email.

## Challenge 3 – Generated SQL (PostgreSQL) for `users`

```sql
CREATE TABLE "users" (
  "id" INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "name" varchar NOT NULL,
  "email" varchar UNIQUE NOT NULL CHECK (email LIKE '%_@_%._%')
);
```

- `GENERATED BY DEFAULT AS IDENTITY` – PostgreSQL's auto-numbering (my DBML `increment`)
- `PRIMARY KEY` – unique and never empty
- `UNIQUE` – no two users can share an email
- `CHECK (...)` – rejects emails without the basic `x@y.z` shape

## Questions

**What does NOT NULL mean?**
The column must always have a value – an insert that leaves it empty is rejected. E.g. `users.name` is NOT NULL so a nameless user can't be created, while `orders.courier_id` deliberately allows NULL to mean "not assigned yet".

**What does DEFAULT mean?**
The value the database fills in automatically when an insert doesn't provide one. E.g. `created_at DEFAULT now()` stamps the current time, `quantity DEFAULT 1` assumes one of each, and `status DEFAULT 'placed'` means every new order starts in the right state.
